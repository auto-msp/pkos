# 9. Canonical Data Architecture

**SOW §6–§20, §87, §90 · Status: `IMPLEMENTED AND RUNNING`**

Not a proposal. `pkos/02-canonical/pkos-store/` holds 1,529 objects with all invariants passing.

## 9.1 The authority decision

**One canonical structured store: SQLite.** One authoritative copy, mirrored to JSONL.

Why SQLite over Postgres, given the SOW allows either:

| Criterion | Verdict |
|---|---|
| §124 vendor independence | single file, no daemon, no server process to keep alive for 20 years |
| §7 inspectable | `sqlite3 file.db .dump` → plain SQL text, anywhere, forever |
| §91 exit strategy | JSONL mirror regenerated by one command; no export tooling to maintain |
| Scale | 1,529 objects now; ~20k URLs + ~17k files + email is comfortably within SQLite by two orders of magnitude |
| Operations | zero. No user, no port, no backup daemon, no version upgrade that rewrites your data |

Postgres becomes right when there are concurrent writers or pgvector at scale. **Both live in the derived plane**, which is explicitly allowed to be anything — Postgres, Qdrant, OpenSearch — without touching canonical authority. Choosing Postgres for canonical today would buy nothing and cost a permanent daemon.

The dangerous alternative the SOW warns against — the only authoritative copy inside an opaque database — is avoided by the JSONL mirror, not by the database choice.

## 9.2 Three planes, physically separated

```
$PKOS_ROOT/
  evidence/    IMMUTABLE, content-addressed by sha256, append-only
    blobs/aa/bb/<sha256>          the path IS the hash
  canonical/   THE AUTHORITY
    canonical.sqlite3
    mirror/*.jsonl                26 files, one per table
  derived/     REBUILDABLE — deleting it is a recoverable act
    fts.sqlite3
```

Physical separation, not just logical: `rm -rf derived/` is safe **by construction**. The smoke test proves it by deleting the entire derived plane and recovering with one command. Each plane carries a plain-text marker file explaining what it is, for whoever opens this in 2036 with no tooling.

## 9.3 Identity and versioning

`object_id = KB-00000001` — allocated transactionally from `id_sequence`, never derived from a path, filename, provider, rowid, vector id or URL. Every object also carries a **uuid4**: the KB- id is the human-facing citable handle, the uuid is what makes two machines' allocations safely mergeable if the store is ever forked and rejoined.

`version_id = KB-00000001:v01`. Changed content creates a **new version under the same object id** — proven by test: re-ingesting a modified file yields `versioned=1, created=0`. Identical content creates nothing: `created=0, unchanged=6`.

## 9.4 26 tables

Identity/registry: `schema_meta` `id_sequence` · Source identity: `source` `account` `profile_workspace` `source_object` · Evidence: `evidence_blob` · Knowledge: `object` `object_version` `provenance` `event` `relationship` `claim` `claim_evidence` · Integrity: `conflict` `duplicate_link` · Operations: `acquisition_manifest` `processing_manifest` `dead_letter` `audit_event` `credential_registry` `sync_state` · Historical web: `url` `url_visit` `web_snapshot` · Derived: `derived_index_registry`.

Design decisions worth naming:

**`content_hash` and `evidence_hash` are different columns.** A bookmark is a record *inside* a `bookmarks.html` blob. Forcing its content hash to be a blob address conflated "hash of this record" with "which raw bytes it came from". This surfaced as a foreign-key failure during testing — a modelling error caught by the constraint, which is what constraints are for.

**Relationships are first-class rows** with their own confidence, provenance, creator and validation status, so an AI-asserted edge is never indistinguishable from a human-asserted one.

**Conflicts are recorded, never auto-resolved.** `conflict.status` starts `OPEN` and only a resolution event moves it.

**Duplicates are linked, never deleted.** `object.is_duplicate_of` marks the alias; the alias keeps its own provenance and stays queryable. 9 links exist in the live store; the `duplicates_linked_not_deleted` invariant fails if any alias ever disappears.

**Credentials store location, never value** — `storage_location` says *where* a secret lives. A validate check greps for anything resembling a secret value and fails if found.

## 9.5 Enforced invariants (all passing on 1,576 versions)

`every_object_has_current_version` · `every_version_has_provenance` · `version_chains_intact` · `every_object_has_event_history` · `account_boundaries_preserved` · `duplicates_linked_not_deleted` · `conflicts_surfaced` · `no_secret_values_stored` · `derived_indexes_registered` · and with `--deep`, a full re-hash of every evidence blob (74 verified, 0 missing, 0 corrupt).

## 9.6 The provenance chain, end to end

```
ANSWER → object → object_version → provenance → source_object → evidence_blob (sha256) → the original bytes
```

Every one of the 1,576 versions has exactly one provenance row. The ratio is checked, not assumed.

## 9.7 Schema versioning and migration

`schema_meta` carries `schema_name`, `schema_version`, `migration_path`, `compatibility_rules`. Rule: additive-only within a major version; a breaking change requires a major bump and a forward migration **testable against the JSONL mirror**. The mirror is what makes migrations verifiable rather than hopeful.
